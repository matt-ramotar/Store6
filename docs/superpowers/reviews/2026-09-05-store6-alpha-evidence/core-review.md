## C1 — P2: Closing Store does not cancel a get suspended before its fetch ticket

**Evidence class:** source-proven control-flow defect; deterministic reproduction proposed, not executed. Confidence high in behavior and medium-high in severity.

**Locations:** `core/src/commonMain/kotlin/org/mobilenativefoundation/store6/core/internal/KeyEngine.kt:4674-4684` (get enters caller context, checks closure once, then suspends and can return); `KeyEngine.kt:2203-2214` (bookkeeper read before snapshot); `KeyEngine.kt:2151-2157` (hydration and write-lock wait). `core/src/commonMain/kotlin/org/mobilenativefoundation/store6/core/internal/RealStore.kt:97-102,166-171,184-186` confirms that get is called directly and close only cancels storeJob. The declared promise is `core/src/commonMain/kotlin/org/mobilenativefoundation/store6/core/Store.kt:170-175`.

**Trigger:** Use a Bookkeeper decorator that delegates normally but can pause exactly one `status` call on a cancellable `CompletableDeferred`. Seed key K with a successful `store.get(K)`. Arm the gate. Launch `store.get(K, Freshness.LocalOnly)` in an independent caller scope and wait for the status gate to be entered. Call `store.close()` while the gate remains closed. The get remains suspended. Releasing the gate lets it return the seeded value because the skip branch never checks closure again. This uses a legitimate suspending Bookkeeper read; it does not require a noncooperative fetcher or a SourceOfTruth that violates first-emission requirements.

**Consequence:** A value request waiting on persistence work outlives Store closure, contrary to the explicit cancellation promise. It can retain the caller and adapter resources indefinitely and can deliver data after the owning Store is closed. Fetch-ticket waits happen to work because their deferred is parented to engineJob; earlier waits are not.

**Counter-evidence and attempted refutation:** `StoreCloseLifecycleTest.kt:22-64` verifies cancellation only after `fetchStarted.await()`, when a get is awaiting its engine-owned ticket. The post-close test covers calls started after closure, which this finding does not dispute. Stream explicitly registers a closeSignal handler at `KeyEngine.kt:2237-2238`, which supports the missing equivalent in get. This is not a claim that close must interrupt an already committed NonCancellable persistence atom or prevent every return racing closure; the trigger parks before a read can complete and leaves it parked after close.

**Narrow fix:** Run the whole get operation in a child request scope that is cancelled by both caller cancellation and Store close, disposing the close registration on exit. Preserve fetch sharing and the intentional noncancellable commit tails. Do not cancel the caller's containing job as a substitute for cancelling this one operation.

**Deterministic acceptance:** With the status gate still closed, close must complete the get with `CancellationException("Store is closed.")`, and the gate's cancellation/finally signal must run. Assert no returned value, no fetch, and no leaked request scope. Repeat for first hydration and a read waiting for writeLock. Retain the existing ticket-wait and post-close exact-message tests. No sleeps or probabilistic timing are needed.

**Uncertainty:** This review did not execute the fixture. If the intended contract deliberately excludes persistence waits from “value requests waiting on in-flight work,” that restriction is absent from the current public contract and would require an explicit product/API ruling rather than assuming the test's narrower coverage is the contract.

## C2 — P2: Bookkeeper read failures escape the Store failure channels

**Evidence class:** source-proven escape path; whether status must instead be operationally infallible is a contract ambiguity requiring resolution. This is a candidate for challenge before a release-blocking classification.

**Locations:** `core/src/commonMain/kotlin/org/mobilenativefoundation/store6/core/internal/KeyEngine.kt:2203-2205` and `2239-2247`: the initial stream snapshot invokes `Bookkeeper.status` outside any retrieval-error conversion. `KeyEngine.kt:4674-4678` does the same for get. Other reads occur at `KeyEngine.kt:1240` and `2153`. `core/src/commonMain/kotlin/org/mobilenativefoundation/store6/core/seam/Bookkeeper.kt:21-31,54-58` explicitly makes recordSuccess, recordFailure, and forget infallible, permits maintenance failures, and does not specify status failure behavior. `core/src/commonMain/kotlin/org/mobilenativefoundation/store6/core/Store.kt:7-11` states the one-failure-channel rule.

**Trigger:** Install a Bookkeeper whose `status(K)` throws a storage read exception while its other methods fulfill the seam. Collect `store.stream(K, Freshness.LocalOnly)`: the exception is thrown from the flow before its first result. `store.get(K, Freshness.LocalOnly)` throws the original exception instead of StoreException. The engine's stream-only SourceOfTruth failure recovery is not reached. A later status failure from active stream delivery similarly cancels its producer.

**Consequence:** A durable bookkeeping read outage can terminate an application collector through an unexpected exception channel and bypass StoreError.Persistence handling. This is not the explicitly documented defensive behavior for an invalid throwing Overlay or telemetry sink.

**Concrete integration evidence:** Root independently identified `file/src/commonMain/kotlin/org/mobilenativefoundation/store6/file/FileBookkeeper.kt:169-181,320-337`: status performs recovery/file-system reads without absorption. File is outside the initial-alpha allowlist, so that is evidence that the seam implementation exists, not a claim that alpha's SQL adapters exhibit this trigger. Independently inspected SQLDelight (`sqldelight/.../SqlDelightBookkeeper.kt:67-82`) and Room (`room/.../RoomBookkeeper.kt:96-155`) absorb ordinary status storage exceptions and return null. Those published adapters reduce initial-alpha exposure but do not resolve the public seam's missing failure contract.

**Counter-evidence and attempted refutation:** No core status-exception test was found. Core tests use status gates and normal status results; failure tests exercise the fallible maintenance methods and SourceOfTruth reads. SQL adapter absorption suggests status may have been intended to be infallible. However, the interface enumerates other infallible operations while omitting status, and a repository implementation can throw from status. Therefore the escape itself is certain, while the choice between fixing core or tightening all seam implementations remains unresolved.

**Narrow fix:** Choose and document one status-failure contract, then enforce it consistently. Preferred preservation of Store's current failure channel is to classify non-cancellation status failures as Persistence and route them through get's StoreException and stream's live error/recovery path. Do not silently treat a failed status read as proof that a key is fresh. If status is deliberately infallible instead, specify the conservative unknown-state behavior and make every library Bookkeeper comply.

**Deterministic acceptance:** A status decorator fails once then recovers. Get must follow the chosen typed contract; stream must not leak the storage exception and must recover without a new subscription if the existing live-stream contract is retained. Include active-stream status failure, initial status failure, and cancellation transparency. Add a concrete cold FileBookkeeper recovery-failure test if that implementation retains read I/O in status. Existing Room/SQLDelight fallback tests must retain their explicit semantics.

## Dismissed or unpromoted hypotheses

- Default memory growth is an accepted, explicit limit. InMemorySourceOfTruth retains canonical cells, and InMemoryBookkeeper retains per-key records/watermarks. StoreBuilder now says maxIdleKeys bounds engines rather than those stores. No new “unbounded cache” defect is claimed.
- The stale-main invalidateResident hook bug is fixed in the reviewed branch, with an `invalidated` guard and dedicated suppression tests. The old get stale fallback after a newer apply is also fixed and has JoinedFetchFailureResidenceAdvanceTest.
- Fetch telemetry throwing can cancel ticket publication, but StoreTelemetry explicitly requires non-blocking no-throw handlers. It is not promoted as a supported-use defect.
- Same-value source notifications cannot distinguish equal external content from a writer echo. The attribution contract states this limit, and the engine has substantial exact-row, raw-cutoff, newer-row, and cancellation coverage. No contrary concrete schedule survived this pass.
- Source reader self-cancellation stops the shared reader without producing a Persistence error. SourceOfTruthFailureConformanceTest.readerCancellation_cancelsWithoutPersistenceEmission pins no retry/no error, so this is not promoted without a different explicit liveness ruling.
- FakeSourceOfTruth suppresses delete notifications when a row is already absent (`testing/.../FakeSourceOfTruth.kt:45-68`), while the contract language refers to any matching delete and the default implementation versions null rewrites. The kit tests deletion only after a non-null value. This is a small contract-interpretation gap, not established alpha runtime harm, so it is not included among findings.
- Negative Freshness.MaxAge durations are accepted and can make a sequence of NotModified responses perpetually unsatisfiable. No constructor validation or negative-duration test was found. Whether negative duration is intended invalid input, and whether positive very small bounds need a retry limit, was not established. Not promoted without a deterministic policy test and contract decision.
- StreamDelivery.pendingFailureHandoffs is an ArrayDeque. Several paths flush it after current-row/absence delivery. A sustained schedule that grows it without corresponding flushes was not proven. An unboundedness finding based only on the container type would be unwarranted.
- The unpublished extension probe retains per-key gates and uses unlimited reader delivery channels; MetricsTelemetry uses unsynchronized increments. These examples are not included in the alpha publication surface and were not promoted into alpha blockers.
