## S1 — P1 for the Swift facade: maintenance storage errors are fatal instead of catchable

**Evidence class:** source-proven bridge path, including the exact pinned SKIE implementation; runtime crash not executed. **Release scope:** outside the current Maven initial-alpha allowlist. Fix before distributing or representing the Swift facade as supported; do not automatically expand the alpha artifact roster to include it.

**Affected locations:** `store6-swift/swift/Sources/Store6/StoreClient.swift:65-86` calls all six Kotlin maintenance methods directly. Those core interface methods have documentation `@throws` clauses, not executable `@Throws` annotations. The generated contract explicitly permits only cancellation conversion at `store6-swift/api/swift/skie/Store6Kotlin.h:582-623`. In contrast, `store6-swift/src/commonMain/kotlin/org/mobilenativefoundation/store6/swift/SwiftInterop.kt:141-151` provides the annotated storeGet wrapper, and StoreClient uses it at `StoreClient.swift:49-55`.

**Trigger:** Wrap a real Kotlin Store configured with a SourceOfTruth whose delete reports a storage failure. Swift calls `try await client.clear(key)` inside do/catch. Core types the failure as StoreException(Persistence), but the direct interface's bridge does not declare StoreException as checked. The same happens for an invalidation whose Bookkeeper stale-mark/watermark write fails, and for namespace/all deletion or bookkeeping cleanup failures.

**Consequence:** The failure escapes as an unhandled Kotlin coroutine exception rather than reaching the Swift catch. The default Kotlin/Native unhandled-exception path terminates the application. Swift's `async throws` surface by itself does not convert arbitrary Kotlin exceptions.

**SKIE counter-hypothesis refuted against pinned primary source:** The repository pins SKIE `0.10.13` in `gradle/libs.versions.toml:20`. That exact tag was fetched read-only from Touchlab's source. [SuspendKotlinBridgeCheckedExceptionsGenerator](https://github.com/touchlab/SKIE/blob/0.10.13/SKIE/kotlin-compiler/linker-plugin/src/main/kotlin/co/touchlab/skie/phases/features/suspend/kotlin/SuspendKotlinBridgeCheckedExceptionsGenerator.kt) reads the original function's `@Throws`; missing annotation produces an empty checked-exception list. [SuspendKotlinBridgeBodyGenerator](https://github.com/touchlab/SKIE/blob/0.10.13/SKIE/kotlin-compiler/linker-plugin/src/main/kotlin/co/touchlab/skie/phases/features/suspend/kotlin/SuspendKotlinBridgeBodyGenerator.kt) passes that list to the runtime. [Skie_SuspendHandler](https://github.com/touchlab/SKIE/blob/0.10.13/SKIE/runtime/kotlin/src/commonMain/kotlin/co/touchlab/skie/runtime/coroutines/suspend/Skie_SuspendHandler.kt) separately catches cancellation, converts a Throwable only if it matches the list, and otherwise rethrows it. Thus the generated async wrappers at `Store6Kotlin.swift:340-385` supply cancellation support, not blanket error protection. This is consistent with the committed header and existing storeGet rationale.

**Existing tests:** `store6-swift/swift/Tests/Store6Tests/StoreClientTests.swift:50-58` exercises successful maintenance only. Fetch-failure and conversion tests exercise get's correctly annotated wrapper. Neither tests maintenance persistence failures. Passing those tests cannot refute this path.

**Narrow fix:** Add dedicated Kotlin wrappers for the six maintenance operations with the declared recoverable exception set, route Swift facade methods through them, and apply the same StoreFailure mapping used by get. Regenerate the bridge dumps from source. Core interface annotations are an alternative API change, but the existing wrapper pattern avoids silently changing the core ABI surface during a facade fix.

**Deterministic acceptance:** A Kotlin fixture exposes a real Store with one failure injector per maintenance operation. For each facade method, Swift must catch StoreFailure.persistence with retained diagnostic/cause information, and the test process must remain alive. Include cancellation mapping to CancellationError, success behavior, and failure-after-earlier-step semantics. Run crash-sensitive regressions in an isolated subprocess until the bridge fix is in place, so a first-red process termination is captured rather than obscured by a suite retry.

## S2 — P2 for the Swift facade: closed-store get is outside its declared exception set

**Evidence class:** source-proven undeclared-exception path; runtime not executed. Same prerelease scope as S1.

**Locations:** `SwiftInterop.kt:146-151` declares StoreException and CancellationException only. `core/src/commonMain/kotlin/org/mobilenativefoundation/store6/core/internal/RealStore.kt:189-193` throws IllegalStateException when already closed, using the factory in `core/.../internal/StoreLifecycle.kt:20-21`. `StoreClient.swift:45-55` cannot catch an exception that the bridge never converts. The generated wrapper annotation contract at `store6-swift/api/swift/skie/Store6Kotlin.h:1285-1289` confirms the same two declared classes.

**Trigger:** Create a Swift StoreClient, call close(), then `try await client.get(key)` inside do/catch. The Kotlin IllegalStateException is not a subtype of either declared exception; pinned SKIE rethrows it instead of delivering an NSError. No failing persistence adapter is necessary. Post-close maintenance has the same problem through S1's unannotated methods.

**Additional lifecycle surface:** `store6-swift/swift/Sources/Store6/StoreStates.swift:27-36` calls the unannotated nonsuspending `storeStates`, which immediately calls `store.stream` at `SwiftInterop.kt:62-67`. Calling states after close can therefore hit the same unhandled IllegalStateException before an AsyncSequence is returned. The facade needs one explicit closed-state contract covering reads, states, and maintenance, rather than fixing only one await call.

**Counter-evidence:** Core post-close tests correctly expect IllegalStateException; they do not cross the Swift bridge. Existing StoreClient tests do not invoke an operation after close. Cancellation of an operation that is already active is a different exception and is correctly included in storeGet's list. The Swift fetch-closure cancellation limitation is already explicit in StoreClient.swift:19-21 and the module README; it is not a new defect.

**Narrow fix and acceptance:** Make closed-store behavior catchable/representable at every facade entry. Include IllegalStateException in the appropriate declared wrapper contract or map it to an explicit facade-level closed-state result without adding an invented StoreError variant. Define what the nonthrowing states constructor returns for a closed store. Verify get, each maintenance operation, and both creating/iterating states after close in Swift with process-survival assertions. Preserve the existing Kotlin exact-message contract.
