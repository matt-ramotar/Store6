## Findings

### A1 — P1: SQLDelight can commit a mutation and then throw caller cancellation

- **Locations:** `sqldelight/src/commonMain/kotlin/org/mobilenativefoundation/store6/sqldelight/internal/DriverAccess.kt:22-51`; `sqldelight/src/commonMain/kotlin/org/mobilenativefoundation/store6/sqldelight/SqlDelightSourceOfTruth.kt:101-148`.
- **Trigger:** after cancellable driver admission, a synchronous row callback writes the row, cancels the caller Job without throwing, and returns. The transaction commits and publishes afterCommit signals. The enclosing `withContext(HeldDriverAccess(...))` remains parent-cancellable and can throw cancellation while completing its child coroutine.
- **Consequence:** the database has changed although the mutation throws. This violates `core/src/commonMain/kotlin/org/mobilenativefoundation/store6/core/seam/SourceOfTruth.kt:21-31`. Core explicitly terminalizes the write as cancelled and skips its normal committed bookkeeping/convergence path (`KeyEngine.kt:1451-1463`, `1484-1508`). The same shared boundary surrounds deletes and Bookkeeper maintenance operations. `withTransaction` checks cancellation at the end of its block, but still has a cancellation window during the subsequent transaction commit/afterCommit phase.
- **Evidence:** source-proven. The pinned coroutines version is 1.8.1. Its [withContext implementation](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/1.8.1/kotlinx-coroutines-core/common/src/Builders.common.kt) uses an undispatched child even when the dispatcher is unchanged. Its [undispatched completion implementation](https://raw.githubusercontent.com/Kotlin/kotlinx.coroutines/1.8.1/kotlinx-coroutines-core/common/src/intrinsics/Undispatched.kt) checks the cancelled completion state after the synchronous block returns. This independently supports the prior review's cancellation candidate; the prior reported execution was not rerun or counted as current evidence.
- **Counter-evidence:** `SqlDelightAtomicityTest.kt:180-196` throws a CancellationException *inside* the user transaction, proving rollback of that path. It does not cancel the parent while permitting the transaction to return normally. The no-suspension restriction does not remove the coroutine-completion check.
- **Narrow fix:** make the acquired committing boundary one outer `NonCancellable + HeldDriverAccess` context, after cancellable admission. Preserve cancellation before admission and rollback when the callback explicitly throws. An inner shield that returns through the existing cancellable outer context leaves the boundary open.
- **Deterministic acceptance:** capture the actual caller Job outside a write callback; write a row, cancel that Job inside the callback, return normally, and record whether the `write` call returned or threw before enclosing coroutine completion. Require normal return plus the committed row, or a throw plus rollback. Repeat for delete variants and maintenance methods, and inject cancellation from a transaction commit callback for `withTransaction`. Confirm explicit thrown cancellation still rolls back and queued admission remains cancellable.

### A2 — P1: Realtime Upsert can attach its ETag to a different value

- **Locations:** `realtime/src/commonMain/kotlin/org/mobilenativefoundation/store6/realtime/RealtimeBinding.kt:72-76`; `core/src/commonMain/kotlin/org/mobilenativefoundation/store6/core/internal/KeyEngine.kt:1622-1645`.
- **Trigger:** a fetch is in flight for the key. Upsert commits pushed value `v2`, a fetch commits value `v1` with tag `e1` after the apply call releases the engine write lock, then Upsert calls `confirmFresh(key, e2)`.
- **Consequence:** the resident pair becomes `v1/e2`. A subsequent conditional request with `e2` can return NotModified and indefinitely revalidate `v1` although the server's `e2` belongs to `v2`. The binding mutex serializes callers of one binding, but does not cover engine fetch commits or other binding instances.
- **Evidence:** source-proven interleaving, not executed. `Transitions.kt:199-211` preserves the existing fetch slot when applying the pushed value. `Transitions.kt:145-168` permits that fetch's later commit while the clear epoch remains unchanged. `KeyEngine.confirmFresh` assigns the supplied tag to whichever resident value exists when it acquires the write lock; it carries no expected revision/value token. Core's network 304 path has an explicit launch-revision check (`KeyEngine.kt:1771-1803`), which this path lacks.
- **Counter-evidence:** `RealtimeBinding.kt:20-24` explicitly permits a later fetch to win source authority. That does not make a mismatched value/tag pair correct. `RealtimeBindingLifecycleTest.kt:94-134` tests serialization through one mocked handle; it does not race an actual engine fetch. `RealtimeAdoptionTest.kt:78-97` checks ETag forwarding only without concurrent writes.
- **Narrow fix:** add an engine operation that atomically applies the value and its freshness/ETag under the same write lock, or return a commit identity from apply and condition confirmation on that identity. Retain the explicit policy on later fetch authority. Protecting only the binding mutex cannot close this race.
- **Deterministic acceptance:** construct the package-internal RealtimeBinding with a wrapper over a real engine write handle. After delegated apply returns, release and await a previously blocked fetch before allowing wrapper apply to return. Then let confirmFresh run. Assert a coherent resident value/tag pair and perform a conditional refetch whose server returns NotModified only for the actual current server tag. Also test two adopting bindings on one key and invalidation between apply and confirm.

### A3 — P2: Default Paging refresh key points at a neighboring page

- **Locations:** `paging-androidx/src/commonMain/kotlin/org/mobilenativefoundation/store6/paging/StorePagingBuilder.kt:18-21`, `65-72`.
- **Trigger:** use the default forward-only configuration. Load page 1 with `prevKey=null`, `nextKey=2`, access an item so the state has an anchor in page 1, then invalidate or refresh.
- **Consequence:** the next generation starts at key 2. Because the default prevKey function always returns null, page 1 cannot be recovered by prepend. The anchored visible content disappears. A generic pagination key cannot be reconstructed from either adjacent key without an application-specific inverse.
- **Evidence:** source-proven mapping. `StorePagingSource.kt:23` delegates directly to this default; `34` passes the returned key unchanged to the application pageKey function.
- **Counter-evidence:** `StorePagingSourceTest.kt:340-367` constructs an anchor in page 2 but asserts refresh key 1. This pins the neighboring-key implementation rather than asserting preservation of the anchor's items. The sample uses a headless snapshot flow and no item access to establish a real viewport anchor (`paging-androidx/sample/.../Main.kt:102-132`, `200-239`). Its regeneration checks therefore do not refute the anchored case.
- **Narrow fix:** default to null for a safe initial restart, or require an explicit refreshKey mapping and document the anchor requirement. An application-specific offset/cursor inversion can be used when supplied explicitly.
- **Deterministic acceptance:** build a PagingState anchored in the only forward page, invoke getRefreshKey, perform the resulting Refresh load, and assert the anchor's items remain reachable. Add a real Paging presenter/item-access test that accesses a first-page item before invalidation. Cover a middle anchor for bidirectional keys using an explicit application mapping.

### A4 — P2: GraphQL floating-point equality disagrees with hashes and canonical identity

- **Locations:** `graphql/src/commonMain/kotlin/org/mobilenativefoundation/store6/graphql/GraphQlValue.kt:56-62`; `graphql/src/commonMain/kotlin/org/mobilenativefoundation/store6/graphql/Canonicalization.kt:24-25`; `GraphQlOperationKey.kt:45-57`.
- **Trigger:** build otherwise identical variables with FloatValue(0.0) and FloatValue(-0.0) on JVM. Primitive Double equality makes the two FloatValue objects equal, while their Double hashes differ and their rendered canonical IDs contain `0.0` versus `-0.0`.
- **Consequence:** equal keys split Store cache identity and violate Kotlin equals/hashCode requirements in caller maps/sets. The accepted NaN value also makes FloatValue.equals non-reflexive. On JS, whole Float values additionally render identically to Int values despite the model declaring those types distinct.
- **Evidence:** source-proven from primitive floating-point comparisons, hash delegation and renderer delegation. Not executed in this turn.
- **Counter-evidence:** `GraphQlCanonicalizationTest.kt:262-265` checks Int-versus-Float object inequality only. It does not assert corresponding canonical IDs differ. Existing hash checks cover integer/string insertion-order cases. The documented cross-runtime rendering caveat does not explain the same-JVM equality/hash/identity disagreement or same-JS type collision.
- **Narrow fix:** choose one explicit finite-number identity rule and use it for equality, hashing and rendering. Either normalize signed zero everywhere or distinguish it everywhere. Reject non-finite values. Keep integer and floating identity consistently distinct if that public contract remains.
- **Deterministic acceptance:** test positive/negative zero through FloatValue, GraphQlVariables, GraphQlOperationKey, hash sets and canonical IDs; require equal keys to hash and identify equally. Test NaN/infinities constructor handling. On JS, test `IntValue(1)` against `FloatValue(1.0)` canonical identity as well as object equality.

### A5 — P3: Room README describes a cancellation defect contradicted by its implementation and KDoc

- **Location:** `room/README.md:219-221`.
- **Trigger/consequence:** an adopter reads the stated remaining commit/cancellation defect and its instruction to consult SourceOfTruth KDoc. The KDoc instead promises the root transaction and notification settlement are cancellation-shielded (`RoomSourceOfTruth.kt:195-200`), matching `withDatabaseAdmission` and `runRootTransaction` outer NonCancellable contexts.
- **Evidence:** source-proven documentation contradiction. This is not evidence that Room commits and throws cancellation.
- **Counter-evidence:** exact-boundary tests would establish more than source, but none were run here. The separately noted hypothetical Room-internal CancellationException is not a demonstrated trigger.
- **Narrow fix:** remove or replace the stale README paragraph with the current, verified cancellation boundary. Do not weaken the implementation's exception-atomicity contract on the strength of an old warning.
- **Acceptance:** check the README, KDoc and cancellation tests describe the same before-admission/after-admission behavior and explicit thrown-cancellation rollback.

## Rejected candidates and explicit boundaries

- **Old C-M9, abandoned Paging collectors:** the lifetime mechanism is source-proven: `GenerationWatcher.kt:59-60` creates an independent SupervisorJob; only explicit source/factory invalidation or store closure stops it. Cancelling the Pager flow does not directly own it. However, `PagingSourceFactory.kt:15-18` already explicitly requires factory.invalidate or store.close when abandoning the pager. This is a documented manual-lifecycle limitation, not a newly undisclosed P1 defect. Before Paging ships, provide a lifecycle-safe usage example and test screen disposal with a long-lived store. Automatic ownership would be an API design improvement. Existing invalidation cleanup tests cover the documented explicit action, not automatic disposal.
- **Room-internal CancellationException taxonomy:** Bookkeeper checks caller activity before absorbing a storage-origin cancellation; SourceOfTruth propagates transaction cancellation. No actual Room 3.0.0 storage failure that throws an internal CancellationException while the caller remains active was established. Keep this as an unexecuted hypothesis, not an alpha blocker.
- **Room backpressure:** bounded mutation-echo backpressure and cancellation shielding can retain database admission behind a starved direct reader. The current KDoc explicitly states this behavior. No independent contradiction beyond the accepted design tradeoff was established.
- **SQLDelight crash-window age:** `MetaSidecar.stampWrite` deliberately persists written time and clears ETag in the same transaction as the value. `SqlDelightCrashWindowTest.kt:22-77` explicitly expects known age without recordSuccess while preserving stale-watermark ordering. Do not report this as missing metadata or lost durable invalidation.
- **Room stale persistent ETag after new value/crash:** rejected as a conditional-request poisoning claim because core hydration explicitly strips persisted ETags (`KeyEngine.kt:2176-2182`). Earlier metadata may survive a two-step value/metadata update, but this review did not establish a distinct unsafe behavior beyond the documented non-atomic durability boundary.
- **SQLDelight external query listeners:** adapter reader signals are intentionally instance-scoped; raw SQL/listener changes appear on a new reader collection. KDoc explicitly discloses that limitation. Not an undocumented reactivity bug.
- **GraphQL operation document omitted from key:** one store serves one configured operation and namespaces can be overridden. Cross-store shared persistence needs a deliberate namespace; no uncontrolled cross-store memory sharing was found. Not promoted solely because the document is absent from the default key.
- **Compose state restart/equivalence:** source normalizes structural key identity and MaxAge duration, resets state for actual identity changes, and deliberately excludes age from Data equivalence. Lifecycle stop retains the latest state. No independent implementation defect was established in this pass.
- **GraphQL transport cancellation:** explicit CancellationException propagation is current documented policy. No exception-to-error taxonomy change is recommended absent a concrete transport-specific trigger.
- **Paging cancellation after a selected baseline:** cleanup after Revalidated processing uses a cancellable discard path. A leak may require contended cancellation at its private mutex; no deterministic reachable trigger was established here. Do not promote it alongside the proven baseline-before-cancellation cleanup test.

## Independent challenge of release findings R1, R2 and R4

- **R1 confirmed, with a shipping-scope boundary.** `ci.yml:93-100` waits only for its build-and-test job. The separately triggered Store6 workflow has no dependency relation to publication. Its Apple/Swift/artifact checks cannot prevent publication as configured. The upstream-repository guard does prevent this development fork from publishing; do not report a current bad publication. Before the upstream tag, gate the validation required for the shipping roster. Do not turn every failure in a deferred artifact into an alpha01 requirement merely because that artifact appears in the large Store6 workflow. Existing original successful evidence at the exact immutable release SHA can satisfy a gate if its provenance and applicable matrix are checked; the gate need not force an unrelated duplicate run.
- **R2 confirmed from preserved execution output.** `/private/tmp/store6-alpha-2026-09-05-full-jvm-hosted.log:363` says `:mutations:jvmTest FROM-CACHE`, while line 392 reports `expected=34 executed=34`. The census counts restored XML files. `gradle.properties:3` enables build caching; `store6-full-jvm.yml:35` and `mutations/build.gradle.kts:44-54` do not prohibit cache restoration for the full test task. This proves that this scheduled run did not execute the test body, not that its cached result is false or that no earlier full run exists. Force fresh execution of the scheduled test task while retaining compilation caching, and validate provenance rather than treating XML file count as execution evidence.
- **R4 partially confirmed and narrowed.** BOM, workflow allowlist and explicit alpha01 rows agree. No shipment expansion is justified. The quickstart's exact contradictory surface is `docs/store6/quickstart.md:7-9`, whose blanket memory-bounding promise conflicts with README:14-15 and default unbounded persistence. Missing roster rows for `file`, `ktor` and `mutations-conflicts` leave consumers without the same release-status clarity as the published list, but are not evidence those modules must ship. `store6-swift/README.md:8-12` already explicitly gives a local-build prerelease consumption path, so the missing central roster entry must not be escalated into a false claim of promised ready remote Swift distribution. The green-for wording for paging/opentelemetry requires an explicit release choice; existing green jobs alone do not establish that choice or authorization to add them.
